## สิ่งที่ต้อง Present (10 นาที/กลุ่ม)

### Demo (5 นาที)
1. เปิด GitHub Issues แสดง product backlog
2. อ่าน user story 1 อัน พร้อม acceptance criteria
3. เปิด `docs/architecture.md` (Mermaid render บน GitHub) และอธิบาย
4. รัน validate ให้เห็นสด: `npx @redocly/cli lint docs/openapi.yaml`
   แล้วเปิด spec ใน Swagger Editor

### Defend (3 นาที)
- เลือก 1 endpoint ที่น่าสนใจที่สุดและ defend การตัดสินใจ
  เช่น ทำไมใช้ POST ไม่ใช่ PUT, ทำไม 409 ไม่ใช่ 400
- บอก 1 ข้อที่ AI เสนอแล้วกลุ่ม **ไม่รับ** พร้อมเหตุผล

### คำถาม (2 นาที)
อาจารย์อาจถาม:
- "Endpoint นี้ถ้า user ส่ง request มาโดยไม่ได้ login จะเกิดอะไร"
- "User story นี้ test ยังไงได้บ้าง — AC ข้อไหนจะกลายเป็น E2E test"
- "N:M relationship ใน ER diagram handle อย่างไรใน database"
- "ถ้า user กดปุ่มจองสองครั้งเร็ว ๆ ระบบจะเกิดอะไร spec รองรับไว้ไหม"
- "มี endpoint ไหนใน spec ที่ไม่มี story รองรับไหม ถ้ามี มันมาจากไหน"

## Rubric (5 คะแนน)

| เกณฑ์ | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| **User Stories** | ไม่มี AC | มี AC แต่วัดไม่ได้ | AC วัดได้บางส่วน | AC วัดได้ทุกอัน | AC ครบ + edge cases + ชี้ได้ว่าอันไหนจะเป็น E2E |
| **Architecture** | ไม่มี diagram | มีแต่ไม่สมบูรณ์ | ครบ components | ครบ + relationships | ครบ + อธิบาย data flow ได้ชัดเจน |
| **OpenAPI Contract** | ไม่มี | validate ไม่ผ่าน | ผ่านแต่ขาด error | ผ่าน + error responses | ผ่าน + error + auth + `required` + trace กลับหา story ได้ทุกอัน |
| **AI Judgement** | รับทุกอย่างที่ AI เสนอ | ทิ้งบ้างแต่ไม่มีเหตุผล | ทิ้ง + เหตุผลกว้าง ๆ | ทิ้ง + เหตุผลเฉพาะเจาะจง | + ชี้ได้ว่า AI เดาอะไรที่ spec ไม่เคยบอก |
| **Defense** | ตอบไม่ได้ | ตอบได้แต่ไม่มีเหตุผล | มีเหตุผลบางส่วน | มีเหตุผลชัดเจน | มีเหตุผล + รู้ trade-off |

**คะแนนเต็ม: 5 คะแนน** (เฉลี่ยจาก 5 เกณฑ์)
